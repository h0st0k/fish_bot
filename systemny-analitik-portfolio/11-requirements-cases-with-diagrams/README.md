## 📖 1. Базовый глоссарий модуля (Общий язык команды)

* **Требование** — Описание того, что система должна делать. Обязано быть конкретным и проверяемым.
* **Шаблон** — Готовая форма для заполнения. Позволяет сосредоточиться на смысле, а не на форме.
* **Спецификация (SRS)** — Единый источник правды. Документ со всеми требованиями для крупных проектов.
* **DoR (Definition of Ready)** — Фильтр качества аналитика. Защита разработчиков от неопределённости.
* **DoD (Definition of Done)** — Критерии готовности реализации задачи со стороны инженеров.

## 📝 2. Чек-лист передачи требований в работу (Уровень декомпозиции)

Перед тем как отдать разработанный Use Case «Оформление заказа» в Jira/Kaiten, системный аналитик производит валидацию по 7 ключевым пунктам:

1. **[✔️] Acceptance Criteria написаны и проверяемы** — условия измеримы, тестировщик сразу пишет тест-кейсы.
2. **[✔️] Граничные случаи описаны** — задокументированы ошибочные сценарии (отказ платежа, таймаут шлюза).
3. **[❌] Нефункциональные требования зафиксированы** — *ПРОБЕЛ:* скорость отклика при пиковой нагрузке в вечер пятницы не оцифрована.
4. **[❌] Макеты приложены** — *ПРОБЕЛ:* отсутствует утвержденная ссылка на Figma для экрана корзины.
5. **[❌] API-контракты описаны** — *ПРОБЕЛ:* формат запроса/ответа для платежного шлюза не задокументирован в Swagger/OpenAPI.
6. **[✔️] Связанные требования указаны** — обозначена зависимость от статусов в панели администратора.
7. **[✔️] Приоритет проставлен по MoSCoW** — задача имеет наивысший приоритет **Must** (Обязательно к реализации).

## 🛠 3. Используемый стек инструментов аналитика
* **Jira / Kaiten** — ведение бэклога, декомпозиция User Stories.
* **Confluence / Notion** — документация Use Cases и требований.
* **Swagger / OpenAPI** — фиксация интеграционных контрактов взаимодействия микросервисов.
* **Draw.io / Miro** — визуализация развилок и логики Happy/Alternative Path.
